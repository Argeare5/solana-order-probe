How do Solana leaders order the transactions inside their blocks? We measured it on mainnet, after Alpenglow, with our own probe transactions.

Bursts of 12 identical transactions, with prices dealt at random and a shuffled send order, went straight to each leader's TPU. Then we found every one of them in the block. The order they landed in shows the rule.

01

What we found

Every number on this page is recomputed from the raw data by the analysis in the repository. A rule is claimed only when it beats a permutation null (p < 0.01) and its 95% bootstrap interval excludes 0.5. Both thresholds were set before the data came in.

Priority fee decides, but never strictly

12 / 12

Every leader puts the higher-paying probe first more often than chance: 0.61–0.89 of pairs, depending on the validator. None does it every time.

Timing changes the rule

0.93–0.97

When the whole burst reaches the leader before its window, Firedancer and BAM leaders come close to a strict fee order. When probes arrive while the leader builds, arrival competes with the fee and the share falls to 0.53–0.83.

Equal fee: two families

Agave ↔ FD

At the same price, Agave-based leaders tend to put the earlier-sent probe first (0.56–0.72). Firedancer leaders put the later-sent one first (0.33, p = 0.0005).

Write conflicts follow the fee tighter

12 / 12

Probes that write-lock the same account are ordered by price more strictly than independent probes in the same bursts, for every validator. Independent transactions run on parallel threads, and that blurs the order.

For BAM and Harmonic, the ingress picks the leader

routed

Their nodes advertise a shared ingress as their TPU, with up to 98 nodes behind one address. Probes sent to one leader landed in the blocks of other leaders behind the same ingress.

Repeatable, with honest caveats

2 sessions

A midday and a night session agree on the shares within 0.09 for 10 of 11 validators. Labels near the threshold can flip between sessions; the report says which findings hold in every one.

06

How it was measured

The full design, with what it accounts for and what it cannot tell apart, is in the README.

The probe
  • SetComputeUnitLimit(900), a price, a 0-lamport transfer to a fresh address and a Memo tag: 806 compute units
  • One fee payer per probe, so probes share no writable account (except in the conflict variant)
  • Same instructions, size and cost for all, so reward per cost unit is ordered exactly as the price
The design
  • 12 prices dealt to payers at random every burst, send order an independent shuffle
  • Variants: price ladder, equal price, cheapest first, write conflicts
  • Fired 300 ms before or 100 ms into the window, with 0, 10 or 50 ms between sends
The path
sender→TPU in gossip→leader's block
sender→shared BAM / Harmonic ingress→whichever leader builds
  • QUIC, configured like Agave's own client, over an unstaked connection opened 700 ms before firing
  • A slot clock on the RPC node's first-shred timestamps, about 60–80 ms mean error
The analysis
  • Only probes in one block of the target's window are compared, pair by pair
  • 95% cluster bootstrap over bursts, plus a permutation null within each block
  • Equal-price bursts and a payer-index control give the noise floor; “no rule” is a valid answer

Verify it yourself

Every probe's signature, slot and block position is in data/. Ask any RPC node for the block and find the probe:

Check a block
$ curl -s https://api.mainnet-beta.solana.com \
  -H 'content-type: application/json' -d '{"jsonrpc":"2.0","id":1,
  "method":"getBlock","params":[{{EX_SLOT}},{
  "encoding":"json","maxSupportedTransactionVersion":1,
  "transactionDetails":"signatures","rewards":false}]}'

The signature's position in result.signatures is the block index the analysis uses.

Rerun everything
$ git clone https://github.com/Argeare5/solana-order-probe
$ cd solana-order-probe
$ docker compose up

A dry-run against mainnet (nothing is sent) and the whole analysis, recomputed from the raw data. Real sends need --live and stay under a spend cap enforced in code.

What went wrong, on the record
  • The first slot clock fired 1.8–3.4 slots early. It was rebuilt on the node's first-shred timestamps.
  • A live run was started by mistake during a code check (48 probes). Its fees were recovered from the chain, and the spend ledger moved next to the keys.
  • Four night bursts went out seconds late after a rate-limited RPC call. A late burst is now skipped.
  • Probes that a shared ingress handed to another leader were at first counted for the target. Now only the target's blocks count.

All of it, with numbers: report → What went wrong. The spend ledger matches the chain to the lamport, and what was left went back to the wallet that funded the measurements.
